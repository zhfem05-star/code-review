### 제출

① 목적: 이 코드는 dict 형태의 자료 클래스인데, 소문자로 키를 저장하고 튜플 형태의 값을저장하는 형태인 것 같아. 즉 받는 키를 소문자로 알아서 저장하고 그걸 관리하거나 조회할 수 있는 메서드를 갖는 클래스야.
② 동작 설명: 인자로 받는 애들을 _store라는 orderedDict()라는 형태로 저장하는데, 아마 없는 키를 받아도 알아서 키를 생성하도록 이걸 택한 것 같아. __setitem__이라는 메서드를 보면 _store 자료에 key가 소문자로 입력되고 값에는 원본의 키와 값이 들어가. __getitem__을 보면 key를 알아서 소문자로 만들고 값에 해당하는 튜플 위치를 반환하도록 설정되어 있고 나머지 Dunder들도 그런 기능을 관리하거나 지원하고 있어.
③ 비판적 시각: 아마 원본을 넣어도 소문자로 검색되게 하는 기능 같은데, 근데 이러면 만약 키가 대소문자 차이만 있는 경우 서로 다른 키여도 같은 dict에 접근하는 문제가 생길 것 같아. 나라면 원본 키인 _store[key.lower()][0]에 있는 값까지 원본 키하고 비교까지는 해보고 값을 줄 것 같아

### 채점

① 목적: 부분 충족
맞은 점: "키를 소문자로 정규화해서 저장하고, 대소문자와 상관없이 조회하는 dict 같은 클래스"라는 설명은 정확해요.
빠진 점: 이 클래스가 왜 필요한지가 없어요. HTTP 헤더 이름은 표준(RFC 9110)상 대소문자를 구분하지 않아요. 서버에 따라 Content-Type, content-type, CONTENT-TYPE 중 무엇으로 보낼지 모릅니다. 그래서 response.headers['content-type']이 항상 동작하게 하려고 만든 클래스예요. 맥락 설명에 적은 response.headers와 연결했으면 충족이었어요.
놓친 디테일: 원래 키도 함께 저장하는 이유는 출력하고 순회할 때 사람이 쓴 케이스를 그대로 보여주기 위해서예요. 47번 줄 __iter__가 _store의 키(소문자)가 아니라 튜플의 0번(원래 키)을 꺼내는 게 그 증거예요.
② 동작 설명: 부분 충족
__setitem__ (38번 줄): 정확해요. 다만 입력→처리→출력 흐름으로 예를 하나 들었으면 더 좋았어요. 예: cid['Content-Type'] = 'json'을 하면 _store['content-type'] = ('Content-Type', 'json')이 됩니다.
__getitem__ (41번 줄): 대체로 맞아요. "튜플 위치를 반환"보다는 "튜플의 [1], 즉 값을 반환"이 정확해요. 키가 없으면 _store에서 KeyError가 그대로 올라온다는 점까지 말하면 완성이에요.
❌ 틀린 부분 (30번 줄): OrderedDict는 "없는 키를 알아서 생성"하는 자료구조가 아니에요. 그건 defaultdict예요. OrderedDict는 삽입 순서를 보존하려고 쓴 거고, 여기서는 헤더 순서를 유지하는 역할이에요. 파이썬 3.7 이전에는 일반 dict가 순서를 보장하지 않았기 때문에 생긴 역사적 선택이라, 지금은 일반 dict로도 충분해요.
"나머지 Dunder들도 그런 기능을 지원한다"는 평가 대상에서 제외했어요. 무엇을 하는지 말하지 않았으니까요.
③ 비판적 시각: 미충족
지적 내용 자체에는 쓸 만한 부분이 있어요. 대소문자만 다른 두 키가 들어오면 하나가 조용히 덮어써지는 것은 맞아요. 예를 들어 CaseInsensitiveDict({'A': 1, 'a': 2})는 길이가 1이에요. docstring 18~20번 줄도 이 경우를 "behavior is undefined"라고 직접 경고하고 있어요. 이걸 "조용한 데이터 유실 위험"으로 짚었다면 주의할 점으로 인정했을 거예요.
하지만 제안한 수정은 클래스의 목적을 깨요. 원래 키까지 비교하면 'Content-Type'으로 저장된 헤더를 headers['content-type']으로 조회할 때 실패해요. 그러면 그냥 일반 dict가 됩니다. 대소문자만 다른 키가 같은 칸에 들어가는 건 버그가 아니라 설계 의도예요.
트레이드오프를 하나도 다루지 않았어요.
