## 2. 리뷰 코멘트 (심어 둔 문제 전체 6개 + 심각도)

### C1. [L71] 🔴 path_count 갱신이 락 바깥 → 데이터 레이스(UB)
- 왜 문제인가: L73의 mutex는 status_count·latency_sum·processed만 감싼다. path_count는 여러 워커가 동시에 operator[]로 쓴다.
  unordered_map은 동시 쓰기를 보호하지 않는다. 같은 키의 ++가 겹치면 갱신 유실, 새 키 삽입 중 rehash(버킷 재배치)와 겹치면 크래시까지 가능.
  "같은 path일 때만" 위험한 것이 아니라, 서로 다른 path라도 같은 맵 구조를 동시에 건드리는 순간 UB.
- 언제 터지나: 경로 종류가 많아 삽입·rehash가 잦을 때. 에러 없이 Top N 수치가 실행마다 조금씩 틀린다. 샘플 23줄로는 안 보인다.
- 대안: L71을 lock_guard(L73) 아래로 이동. 경합을 줄이려면 워커마다 로컬 Stats를 채우고 join 후 한 번만 병합(락 자체가 필요 없어짐).
- 재현: 고유 경로 100만 개짜리 로그(uniq.log, /api/items/<랜덤>) + 워커 8개, path_count 합계를 출력하는 변형으로 3회 실행
    processed lines: 1000000 / path_count sum: 999941
    processed lines: 1000000 / path_count sum: 1000000
    processed lines: 1000000 / path_count sum: 999963
  → 락 안의 processed는 항상 정확하고, 락 밖의 path_count만 실행마다 59개, 37개씩 사라짐. 에러도 경고도 없음.
  (gen_data.py의 경로 504개 데이터로는 5회 모두 정확했음 → 레이스는 "테스트가 통과해도 없는 게 아니다")

### C2. [L26-29] 🟠 나머지 줄 버림 + 줄 수 < 워커 수면 전부 버림
- 왜 문제인가: chunk = size / n 은 정수 나눗셈이라 마지막 size % n 줄이 어느 워커에도 배정되지 않는다.
  size < n 이면 chunk = 0 → 모든 워커가 [0, 0) 구간 → 한 줄도 처리하지 않고 정상 종료.
- 언제 터지나: 줄 수가 워커 수로 나눠떨어지지 않으면 거의 항상. 결과가 "조금" 틀려서 눈치채기 어렵다.
- 대안: 마지막 워커만 end = lines.size()  (조건은 w == num_workers_ - 1)
        또는 올림 분할 chunk = (size + n - 1) / n, end = std::min(begin + chunk, size)  (begin >= size면 스레드 생략)
- 재현:
    input.txt 23줄, 워커 2  → chunk 11 → 22줄 처리 (L23 "GET /api/users 200 8" 누락)
    input.txt 23줄, 워커 8  → chunk 2  → 16줄 처리 (7줄 누락)
    3줄, 워커 2            → chunk 1  → processed lines: 2
    3줄, 워커 8            → chunk 0  → processed lines: 0, exit=0

### C3. [L96 → L26] 🟠 hardware_concurrency()가 0이면 0으로 나누기
- 왜 문제인가: 표준은 hardware_concurrency()를 "힌트"로 정의하고, 알 수 없으면 0을 반환할 수 있다고 명시한다.
  0이 그대로 num_workers_가 되어 L26에서 정수 0으로 나눔 → UB(리눅스에서는 SIGFPE로 즉사).
- 언제 터지나: 일부 컨테이너·임베디드·특수 환경. 개발 PC에서는 절대 재현되지 않는 유형.
- 대안: unsigned n = std::max(1u, std::thread::hardware_concurrency()); 줄 수가 적으면 n = min(n, size)로 상한까지 두면 C2의 chunk=0도 함께 막힘.
- 재현: 워커 수를 인자로 받는 변형에 0을 넣음 → "Floating point exception", exit=136

### C4. [L68-69] 🟠 stoi/stol 예외가 스레드 밖으로 → 프로그램 전체 abort
- 왜 문제인가: L65는 "필드 개수"만 확인하고 "필드 내용"은 확인하지 않는다. 숫자가 아닌 값이면 std::invalid_argument,
  범위를 넘으면 std::out_of_range. 워커 스레드에서 잡히지 않은 예외는 std::terminate → 지금까지 집계한 결과까지 모두 잃는다.
- 언제 터지나: 실제 nginx·프록시 로그에서 응답 전에 끊긴 요청은 latency가 "-"로 찍힌다. 100만 줄 중 1줄만 이래도 전체가 죽는다.
- 대안: 숫자 파싱을 try/catch로 감싸 skip 카운트 증가, 또는 std::from_chars(예외 없음, 반환된 ec 확인).
- 재현: input.txt 5번째 줄을 "2026-11-26T08:00:03 GET /health 200 -"로 바꿈
    terminate called after throwing an instance of 'std::invalid_argument'
      what():  stol
    Aborted, exit=134

### C5. [L30] 🟡 람다가 lines를 값으로 캡처 → 스레드마다 전체 복사
- 왜 문제인가: [this, lines, ...]는 vector 전체를 워커 수만큼 복사한다. 각 워커는 자기 구간만 읽으므로 사본은 전부 낭비.
- 언제 터지나: 1GB 로그 × 워커 8 → 메모리 8GB 추가 + 스레드 시작 전 복사 시간만큼 지연.
- 대안: [this, &lines, begin, end]. L36에서 run()이 모든 스레드를 join한 뒤 반환하므로 참조 수명이 보장된다(코멘트에 이 근거까지 적기).

### C6. [L89] 🟡 파일 열기 실패를 확인하지 않음
- 왜 문제인가: 경로 오타·권한 문제로 열기에 실패해도 getline이 바로 false → 빈 결과를 "정상"으로 출력하고 exit 0.
- 언제 터지나: 크론·Airflow 같은 배치에서 돌릴 때. exit 0이라 스케줄러가 성공으로 처리하고 빈 리포트가 그대로 다음 단계로 간다.
- 대안: if (!in) { std::cerr << "cannot open: " << argv[1] << "\n"; return 1; }
- 재현: ./agg nope.log → "processed lines: 0 / top 0 paths:", exit=0

### (심어 두지 않았지만 타당한 지적)
- [L65] 🟡 깨진 줄을 조용히 건너뜀 — 사용자 C1. 건너뛴 줄 수를 세서 리포트에 출력하면 C4의 해결(skip 카운트)과 한 번에 정리된다.
- [L48] 🟡 평균이 정수 나눗셈이라 소수점 이하 버림. 의도라면 이름이나 출력에 "(floor)"를 밝히고, 아니면 double로 계산.
- [L73] 🟡 줄마다 락 → 워커가 늘수록 경합. C1 대안의 "워커별 로컬 집계 후 병합"이 성능·정확성 둘 다 해결.

## 3. 좋은 점
- [L36-38] 모든 스레드를 join → 집계가 끝난 뒤에만 결과를 읽는다(사용자 지적). C5의 참조 캡처가 안전한 근거이기도 함.
- [L73] lock_guard(RAII) → 예외가 나도 락이 자동으로 풀린다. 수동 lock/unlock보다 안전.
- [L43] unordered_map을 std::map으로 옮겨 출력 → 실행마다 출력 순서가 같다(diff·테스트하기 쉬움).
- [L51-54] 전체 정렬 대신 partial_sort, n = min(top_n, size)로 경로가 3개 미만일 때도 안전.
- [L47] processed > 0 확인으로 평균 계산의 0 나누기 방지.
- [L84-87] 인자 개수 확인 + usage 출력 + exit 1.

# 부록 A. 오늘 배운 C++ 개념 노트

[mutex는 데이터가 아니라 "코드 구간"을 보호한다]
- C++은 어떤 변수가 어떤 락에 묶였는지 강제하지 않는다. 공유 데이터마다 "모든 접근이 같은 락 안에 있나"를 직접 확인해야 한다. (L71 vs L73)
- 표준 컨테이너(unordered_map, vector)의 동시 쓰기는 그 자체로 미정의 동작(UB). "숫자가 조금 틀리는 것"으로 끝난다는 보장도 없다.

[람다 캡처: 값 vs 참조]
- [x]는 복사, [&x]는 참조. 참조 캡처는 "원본이 스레드보다 오래 산다"는 보장이 있을 때만 안전. (L30, 근거는 L36의 join)
- detach한 스레드에 지역 변수를 참조로 넘기면 댕글링 참조.

[스레드 안의 예외]
- 스레드 함수 밖으로 나간 예외는 다른 스레드에서 잡을 수 없다 → std::terminate → abort. 스레드 안에서 처리하거나 std::async/future로 전달. (L68-69)

[hardware_concurrency()]
- 하드웨어 스레드 수의 "힌트". 알 수 없으면 0. 분모·개수로 쓸 때는 반드시 max(1, …). (L96)

[std::ifstream]
- 열기 실패해도 예외가 없다. if (!in)으로 직접 확인. (L89)
